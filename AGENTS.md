# zot-clean, développement

`zot-clean` aide à mettre de l'ordre dans une bibliothèque Zotero (nettoyage) et à le maintenir (gestion). La lecture, les suggestions de textes et les notes sont laissées aux extensions de Zotero qui s'en chargent déjà (D243). Ce fichier s'adresse à qui développe l'outil. Le `AGENTS.md` que `zc init` écrit dans le dossier de travail d'un utilisateur est un autre fichier, livré avec le paquet.

- Ce dépôt (privé, `zot-clean-atelier`) garde l'historique de travail. Le dépôt public `deubelen/zot-clean`, d'où les utilisateurs installent l'outil, reçoit un commit par version par `outils/publier.sh`, jamais à la main. Aucun détail sur la bibliothèque, la configuration ou la vie de l'auteur dans les fichiers suivis, puisqu'ils sont publiés.
- Une nouvelle étape de nettoyage produit un plan (`plans.Plan`) et laisse `apply.py` l'exécuter. Elle n'appelle jamais `Client.write` elle-même, pour hériter des garde-fous (essai, sauvegarde, synchronisation, journal, reprise, annulation).

## Architecture

- Paquet Python `zot_clean` (dans `src/`), ligne de commande `zc` (D9). Le mécanique vit dans la ligne de commande, le jugement dans les skills livrés avec le paquet.
- Les garde-fous sont dans le code et non dans les consignes, pour ne pas dépendre de l'agent. Simulation par défaut, écriture seulement avec `--appliquer`, sauvegarde récente exigée avant une opération de masse (D15), journal de chaque écriture (D16).
- Lecture sur une copie temporaire de `zotero.sqlite` (+ `-wal`), par un seul module qui contrôle la version du schéma (D12). Toujours filtrer `libraryID = 1` sauf lecture explicite d'un groupe déclaré.
- Écriture uniquement par l'API web via `pyzotero`, lots de 50 au plus, contrôle de version (D13). Jamais d'écriture dans `zotero.sqlite`, jamais de création d'élément hors de l'API (les clés invalides bloquent la synchronisation).
- Supprimer un nom de tag par l'API le retire pour tous ses types. Vérifier d'abord qu'il n'est pas porté en manuel.
- Toute convention de la méthode par défaut (D19 à D25) passe par `config.toml`, jamais en dur dans le code.
- Code portable (D11). `pathlib`, aucune commande propre à macOS sans solution de repli.

## Conventions

- Code, commentaires et tests en anglais (D208, phase 1 du passage à l'anglais). Les textes affichés s'écrivent dans les deux langues par `L(en='…', fr='…')` (D220), les commandes et options sont anglaises d'après `registry.py` (D219), et les anciens noms français refusés avec leur équivalent (D213). L'aide `--help` est en anglais seulement (D215). Les clés et valeurs écrites dans le dossier de travail restent celles de la version 0.3.2 (D209), reliées aux noms du code par des tables explicites (`PLAN_FIELDS`, `KEYS`…). Limiter les deux-points dans les textes rédigés.
- Python 3.11 au minimum, dépendances réduites au nécessaire.
- Tests avec `uv run pytest`, sur la bibliothèque synthétique de `tests/` (D29) et le faux serveur `tests/fake_server.py` (D45). Aucune donnée personnelle dans le dépôt. Les tests qui écrivent pour de vrai sont dans `tests/manual/`, sur le compte de test seulement.
- Commiter après chaque changement d'outil ou de décision.
