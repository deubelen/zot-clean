# Tags

Step 6 handles the whole set of tags in one inventory and one plan. `zc tags inventory` writes `suivi/tags.toml` (the tag rules file), which describes rules by tag name, never by item, and keeps the decisions from one run to the next. This file is authoritative. It also serves later for the triage of the Inbox, which applies the same rules to the new references. `zc tags plan` plans only what remains to be changed, it can be run again after each pass.

It is better to have done the outline of the subjects (steps 4 and 5) first, since concepts and tags that duplicate a theme are judged from the themes of the subjects. This is not required.

The words stored in `suivi/tags.toml` are French in every library (`sort`, `classe`, `decision`, `supprimer`, `garder`, `concept`, `état`, `fusionner`, `évident`, `douteux`, `accepter`, `refuser`, `[automatiques]`, `[importes]`, `[[tag]]`, `[[variantes]]`, `cible`…). On the command line, the actions are written in English (`--action delete|keep|concept|status|merge`) and `zc` stores the French word.

Concepts follow a single convention, which `zc` applies as far as it can in its proposals and which the agent applies to the name it proposes. A concept carries the concept prefix (`#` by default, `zc config show` gives it), is written in lowercase except for a proper noun or an acronym (« #memory », « #Kant », « #ADHD »), in the language of the user (« #embodied cognition » rather than « #cognition incarnée » for an English-speaking user, and the other way round for a French-speaking one, unless a term is established in their field), with spaces between the words rather than hyphens or underscores. `zc` translates nothing. It is for the agent to propose the name in the right language.

Some tags are protected and receive no proposal, namely the technical tags (`_…`), the statuses and marks of the method, the colored tags, those of `[tags] proteges` (protected) in `config.toml`, and those on which a pending filing proposal rests. They change only through an entry added at the explicit request of the user, `zc tags add "<name>" --action delete|keep|concept|status|merge --user`. The tag of the privacy filter (`_privé` in a French library, `_private` in an English one, see `[confidentialite] tags_exclus`) never changes.

The decisions are written by command, without touching the file, with `zc tags accept`, `zc tags reject` and, for a tag that has no entry, `zc tags add`. A tag is designated by its exact name, always between single quotes (`'#attention'`, `'letters/arts'`, `'★'`), or double quotes if the name contains an apostrophe, since a name that starts with `#` would be taken by the terminal for a comment. The names come first, the options after. `zc` refuses a name that is absent from the file and changes only what awaits a decision. A decision already made is changed by hand in the file.

## Procedure

1. **Take inventory.** Run `zc tags inventory`, then read the report `rapports/tags-inventaire-<date>.md` and `suivi/tags.toml`. Done when the command has given the number of tags and of groups to judge.

2. **Global rule of the automatic tags.** Automatic tags are the publishers' keywords, added by Zotero and rarely useful. Present to the user what the rule removes (number of names and occurrences, the most carried) and the exceptions proposed, to be judged next. After their agreement, run `zc tags accept --automatic-rule`. If they prefer to keep these tags, `zc tags reject --automatic-rule`, and point out that they can also hide them in Zotero's tag selector (« Display Automatic »). If there is an `[importes]` section, do the same for the imported keywords (`--imported-rule`), after showing two or three items of the report with `zc show <key>` to verify that they are indeed publishers' keywords. Done when both sections have a decision.

3. **Variants.** The `[[variantes]]` groups bring together names of the same form, brought back to `cible` (target), set as a manual tag.
   - The groups `classe = "évident"` differ only by case, accents, spaces, hyphens or prefix. Check that the target proposed follows the concept convention (lowercase except for a proper noun, language of the user), then present them in a single block, with their number and one line per group. A single approval is enough.
   - The doubtful groups (plural, other difference) are presented in bundles of at most 10, each with a recommendation. A plural can change the meaning (« letter » and « letters », in the sense of literature), recommend rejecting then.
   - Also propose, on your own initiative, the obvious translations (« memory » and « mémoire »). After agreement, write them as a merge, `zc tags add 'memory' --action merge --target 'mémoire'`, or `zc tags accept 'memory' --action merge --target 'mémoire'` if the tag already has a `[[tag]]` entry.
   - After agreement, `zc tags accept --variants '<name>' …` and `zc tags reject --variants '<name>' …`, each group designated by its target or one of its names. If the user changes the target, `zc tags accept --variants '<name>' --target '<target>'`, one group per command.

   Done when the user has judged the groups they wanted to handle now.

4. **Tags to judge.** Each `[[tag]]` carries a proposed fate (`sort`), its count (items), its dispersion (themes of the subjects where its items are), its themes and, in a comment, three titles. For an unclear case, run `zc show --tag <name>`, which shows the items that carry it with their collections.
   - **Statuses and marks** (`sort = "état"`). Tags coming from other habits (« to read », « important »), matched to those of the method. Present them in one block. An item that would receive two statuses keeps the more advanced.
   - **Carried by a single item** (`classe = "évident"`, `sort = "supprimer"`). Present them in a single block with the complete list, which the user can go through.
   - **Concepts** (`sort = "concept"`). Tags spread over several themes, which cross the subjects. Propose for each a name (`cible`) that follows the concept convention, translating it if needed (the name proposed by `zc` takes that of the tag, put in lowercase), and a definition of one or two sentences. After agreement, add the definition to the `# Concepts` section of `plan.md`, under a title `## #name`.
   - **Tags that duplicate a theme** (`theme` filled in, `sort = "supprimer"`). They repeat a collection. When other names of the same form exist (« Emotions » for « emotion »), `zc` brings them together in the `variantes` field of the entry instead of making a `[[variantes]]` group of them. Accepting the entry deletes them with the tag. If the user prefers to keep the tag, accept it with `--action keep`, and the variants are then brought back to it. The items that carry them without being in the theme have been proposed in `suivi/rangement.toml`. Have them judged first (skill `subjects`, step 5), the tag stays in place while they wait.
   - **Other tags**, in bundles of 20, with count, dispersion and titles, each with a recommended fate among `delete`, `keep`, `concept`, `merge` (renamed to `cible`). Keeping is a legitimate fate, the method does not forbid a tag outside its families.
   - A tag cited by a saved search (`recherches`) is removed or renamed only by an explicit decision. Remind the user of this when judging.
   - An automatic tag whose entry awaits a decision escapes the global rule. If it is rejected, the rule removes it.

   After agreement, `zc tags accept '<name>' …` and `zc tags reject '<name>' …`. For another fate or another target than those proposed, `zc tags accept '<name>' --action delete|keep|concept|status|merge --target '<target>'`, one command per fate and target, and the entry moves to source « agent ». Once the two blocks of obvious cases are approved (groups of step 3, tags carried by a single item), `zc tags accept --obvious --except '<name>' …` accepts them at once, except those the user set aside. Before that, name the groups and the tags. Done when the user has judged the bundles they wanted to handle now. The remaining entries block nothing.

5. **Plan.** Run `zc tags plan`. Summarize the report of the plan, that is the number of elements, the colors proposed (section « Colors », « Couleurs » in a French library: the tags of the method at the head of the selector, each on the key of its rank, and the tags already colored that change key), the kinds of change, the tags removed and renamed, the saved searches to update, and the section « To look at » (« À regarder »). Done when the user has explicitly approved this plan.

6. **Back up, trial, apply.** If the last backup is more than 24 hours old, ask the user to close Zotero and run `zc backup`. Then `zc apply <plan> --trial`. The elements of the trial, listed in the report with their tags before and after, cover each kind of change. Check them with `zc show` (tags and their type), tell the user, then `zc apply <plan> --all`. An interrupted command is run again as it is. Done when the full application is made.

7. **Afterwards.** If the report of the plan cites saved searches, remind the user to update them in Zotero. Offer to untick, in Zotero's settings (General) and in those of the browser connector, « Automatically tag items with keywords and subject headings », so that the automatic tags do not come back. Run `zc audit` and run `zc tags inventory` again to see what remains. A new pass is done the same way, from step 3.

To rename or merge a colored tag, the user goes through « Rename Tag… » in Zotero's tag selector, which carries the color over. `zc` colors only the tags of the method, whose colors `zc tags plan` proposes (« Colors » section of the plan). The other colored tags keep theirs, even when they change key.

To go back on an applied plan, run `zc undo <plan>`, summarize the undo report, then follow step 6 with the undo plan. The undo does not change the decisions of `suivi/tags.toml`: `zc tags plan` would propose the same changes again. Ask the user which rules must stay undone and, before planning again, change their decision by hand in `suivi/tags.toml` to `"refuser"` (rejected): `zc tags reject` refuses to overwrite a decision already taken. The colors of the method tags are a rule of their own: if the undo restored the old colors and the user wants to keep them, do not apply a plan that only changes the colors.

A tag presented as « tag confidentiel … » is carried only by items excluded by the filter (the identifier is always written « tag confidentiel <identifier> », in every library). Do not try to find out which. Only the global rules apply to it. If the user wants to change one, they say so, and the entry is added with this identifier as the name, `zc tags add 'tag confidentiel <identifier>' --action delete|keep|concept|status|merge --user`.
